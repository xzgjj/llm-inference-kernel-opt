## 2 路径约定

- 真实权重不进仓库。仓库内 `models/` 只放测试夹具（`tests/fixtures/models/*.gguf`、`build/dev/fake.gguf`）。
- Windows 侧统一放 `D:\ai_model\models\<模型名>\`（`D:\ai_model` 是本机模型落盘根，见其 `README.md`）。
- WSL 侧保留 `/root/llm-src/models/`，与本表 L0 一致；两侧路径映射见 §5。
- 脚本里的默认 `--model` 仍是 L0 路径，未改。跑 L1 时用环境变量覆盖（`LLMOPT_MODEL=...`，见 `scripts/repro.sh`）。

## 4 选型口径（为什么是 8B / Q4_K_M）

- **0.5B 的问题不是旧，是小**：KV 约 12 KB/token，8 路 × 4K 上下文只占 ≈0.38 GB，水位线与抢占在真实负载下几乎不触发；解码数百 token/s，aging 与恢复时延的时间尺度测不准。
- **8B 让压力回到真实区间**：4 路 × 2048 上下文 ≈ 1.18 GB KV，加 4.68 GB 权重落进 8188 MiB 显存的可用区间，TTFT/ITL 进入百毫秒级，`safety_ratio`、`watermark`、chunk 权衡才有可分辨的信号。
- **Q4_K_M 是质量/体积的常规拐点**：向下降到 Q3 会明显伤输出质量，向上 Q5_K_M（5.45 GB）与 KV 挤在一起，8GB 卡不再有余量。

## 5 用法

Windows 侧服务（L1）：

```powershell
.\build\llmopt_server.exe --model D:\ai_model\models\qwen3-8b\Qwen3-8B-Q4_K_M.gguf `
  --host 127.0.0.1 --port 8080 --backend llama --mode off --ctx-tokens 2048 --max-concurrency 4
```

WSL 侧的 0.5B 老路径保持不变（脚本默认值）：`--model /root/llm-src/models/qwen2.5-0.5b-q4.gguf`。Windows 盘符在 WSL 里映射为 `/mnt/d/ai_model/models/qwen3-8b/`，需要跨侧跑时用这个。

注意：本机 `C:\msys64\ucrt64\bin\llama-server.exe` 是 **CPU/OpenCL 构建，不含 CUDA 后端**（启动日志会报 `ggml_opencl: unsupported GPU 'NVIDIA ...'`，`-ngl` 实际不生效）。GPU 全量驻留必须用项目的 CUDA 构建；冒烟只能验证权重与架构可加载。

## 6 依赖与版本边界

- 架构名 `qwen3`。冻结的 llama.cpp `b94959a`（`CLAUDE.md` §3）已在支持列表中，理论上无需升级；实测结论见 §7。
- 后续若接 Qwen4 系（`qwen4exp` 架构），必须升级 llama.cpp 版本 —— 属技术栈变更，走 `CLAUDE.md` §3 / §8 流程，不得自行实施。
