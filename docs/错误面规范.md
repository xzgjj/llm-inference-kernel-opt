# 错误与异常处理规范

版本：v1.0（2026-11-20）　适用：`llm-inference-kernel-opt`　状态：生效
取代：`代码质量评审.md` 中 QC-01/QC-03/QC-05 的错误面条目（其余条目不受影响）

本文件回答四件事：错误怎么分层、消息写什么、第三方错误怎么包、异常在哪里兜。所有新增代码按本文件审查，不满足即视为缺陷。

---



## 1 三层模型

错误从产生到被看见必须经过三层，禁止跳层：

```
领域层   ErrCode + Error{code, message, detail}      ← 产生点：谁失败、为什么、原始 cause
   │      （ErrCode 是稳定契约；Error 是跨层载体；detail 不外发）
传递层   Completion / Delta / ResponseSink            ← 全程携带 Error，禁止退化成裸枚举
   │
边界层   HTTP status + JSON body / CLI 退出码 / 日志   ← 只在这里翻译一次
```

三条硬约束：

1. **跨层只传 `Error`，不传 `ErrCode` 单值**。`ErrCode` 是 `Error` 的字段，不是消息本身。
2. **翻译只发生在边界**：HTTP 状态码由 `http_status()` 单点决定（`common.cpp`），进程退出码由 `main` 单点决定，日志级别由写日志处决定。
3. **同一个失败只翻译一次**。下层已经给出明确语义（如 `KvInsufficient`）时，上层直接透传，不得改名成 `EXECUTION_FAILED` 之类更模糊的码。

### 1.1 Error 结构

```cpp
struct Error {
    ErrCode code = ErrCode::Ok;  // 领域码，跨层不变
    std::string message;         // 给调用方看：发生了什么、涉及哪个字段/请求、合法范围
    std::string detail;          // 给运维看：第三方原始码、操作名、位置；不进 HTTP body
    bool ok() const noexcept;
};
```

- `message` 进 HTTP body（`error.message`），必须能指导客户端决策：是改参数、退避重试，还是不要重试。
- `detail` 只进日志。禁止把文件路径、权重内容、prompt 原文放进 `detail`（见 `docs/ci/log-policy.md` §6.4）。
- 成功路径统一用 `Error{}`（`code==Ok`），不构造带 message 的"成功"。

## 2 规则

| 编号 | 规则 | 反例 |
|---|---|---|
| R1 | 一个码一个含义，不复用 | 用 `PromptTooLong` 表示"没填 --model"（`config.cpp` 旧实现） |
| R2 | `message` 回答"谁、什么、边界值" | "采样参数非法或越界"（不指字段）→ 应写 `max_tokens 必须是整数且在 [1, 4096]` |
| R3 | 第三方码不穿透边界 | 把 `llama_process` 的 `int rc` 一路传到 HTTP |
| R4 | 只翻一次，不层层改名 | `SQL_TIMEOUT → RepositoryFailure → ServiceFailure` 三连 |
| R5 | 保留 cause，不丢原始信息 | 把 `rc=1` 丢掉只留 "前向失败" |
| R6 | 编程缺陷不做翻译 | 断言失败、越界访问包装成 `INVALID_JSON` 返回给客户端 |
| R7 | 状态码单点映射 | 每个 handler 自己 `if` 判 400/500 |
| R8 | 回投与关停事件不许丢 | `mailbox.push()` 返回值被忽略，丢一条 Completion 即永久挂死 |

R2 的写法模板：`<字段/对象> + <违反的约束> + <合法范围或期望>`，例如

- `prompt 不能为空`（已符合）
- `max_tokens 必须是整数且在 [1, 4096]`（已符合）
- `等待队列已满（32/32），请退避后重试`（新增）
- `KV 块不足且无可抢占 victim（free=3 need=17）`（新增）

## 3 领域码表

`ErrCode` 是唯一对外码集。**新增码必须同时补 `http_status` / `error_code_name` / `retryable` 与本表**，否则 CI 视为未完成。

| ErrCode | HTTP | code | 触发点 | 可重试 | message 要点 |
|---|---|---|---|---|---|
| Ok | 200 | OK | — | — | — |
| InvalidJson | 400 | INVALID_JSON | 请求体/字段/Request ID 非法；活跃 ID 重复 | 否 | 字段名 + 合法范围；重复 ID 要明确可换新 id |
| ConfigInvalid | 400 | CONFIG_INVALID | 配置文件/环境变量/CLI 参数非法 | 否 | 来源 + 参数名 + 合法范围 |
| PromptTooLong | 400 | PROMPT_TOO_LONG | 分词结果超上限 | 否 | 当前长度/上限 |
| ContextOverflow | 400 | CONTEXT_OVERFLOW | prompt+max_tokens > ctx | 否 | 两个数都要给 |
| PayloadTooLarge | 413 | PAYLOAD_TOO_LARGE | 请求体超过 4 MB 上限 | 否 | 上限值 |
| ModelNotLoaded | 503 | MODEL_NOT_LOADED | 权重/上下文未就绪 | 是 | 后端 + 失败阶段 |
| KvInsufficient | 507 | KV_INSUFFICIENT | 块不足且无任何可抢占 victim | 否 | free/need |
| KvBelowWatermark | 429 | KV_BELOW_WATERMARK | 临时低于安全水位 | 是 | free/need/watermark |
| QueueFull | 429 | QUEUE_FULL | 准入拒绝（入口判定） | 是 | 当前深度/容量 |
| Cancelled | 499 | REQUEST_CANCELLED | 客户端断开/主动取消 | 否 | 只进日志 |
| ExecutionFailed | 500 | EXECUTION_FAILED | 前向失败、采样失败、批次异常 | 否 | 操作名 + 原始 cause(detail) |
| NotSupported | 404 | NOT_SUPPORTED | 未开放端点或协议能力 | 否 | 端点/能力名 |
| ResourceInsufficient | 507 | RESOURCE_INSUFFICIENT | 启动预算不足/句柄耗尽 | 否 | 需要量/可用量 |
| Timeout | 504 | TIMEOUT | 服务端等待超时（非客户端取消） | 是 | 等待时长 |
| UnsupportedField | 400 | UNSUPPORTED_FIELD | 请求含兼容面外字段 | 否 | 字段名 |
| Unavailable | 503 | SERVICE_UNAVAILABLE | 服务排空/未就绪 | 是 | 当前状态 |
| RateLimited | 429 | RATE_LIMITED | 令牌桶拒绝 | 是 | rps/burst |
| Unauthorized | 401 | UNAUTHORIZED | Bearer 缺失或错误 | 否 | 不泄漏 token |

状态码选择依据：`429` = "现在不行，稍后可以"；`504` = "我们这边慢了"；`499` = "你走了"；三者不得互换。

## 4 第三方错误封装

原则来自 Abseil `Status` 与"在抽象边界翻译错误"的通行做法：**转换点放在同时了解两侧语义的适配器里；转换后只保留调用方需要的区分度；原始 cause 进 `detail` 供诊断；同一次失败不重复翻译。**



### 4.1 llama.cpp

| 第三方信号 | 领域映射 | detail |
|---|---|---|
| `llama_model_load_from_file` 返回 `nullptr` | ModelNotLoaded | `op=load_model path=<basename>` |
| `llama_init_from_model` 返回 `nullptr` | ModelNotLoaded | `op=init_context n_ctx=<n>` |
| `llama_process` 返回非 0 | ExecutionFailed | `op=process rc=<rc>` |
| `llama_batch_ext_add_token` 返回负值 | ExecutionFailed | `op=add_token idx=<idx> seq=<id>` |
| `llama_sampler_sample` 返回负值 | ExecutionFailed | `op=sample output_index=<i>` |
| `llama_tokenize` 返回负值（缓冲不足） | PromptTooLong（仍为负则失败） | `op=tokenize need=<n>` |

实现方式：`runner_llama.cpp` 内 `from_backend(op, rc)` 统一构造，**不把 `int` 返回值带出适配器**。



### 4.2 httplib / nlohmann / spdlog / filesystem

| 来源 | 处理 |
|---|---|
| httplib `listen` 失败 | main 记录 `listen 失败 host/port` + 退出码 3；不抛 |
| nlohmann `parse` 抛异常 | `parse_body` 内 catch → InvalidJson，`detail=exc.what()` |
| spdlog 建 sink 失败 | 降级 stdout，不阻断启动（已有） |
| `std::filesystem` 异常 | `read_gguf_meta` catch → `Error{InvalidJson, "读取模型元数据失败", detail}` |
| `std::thread` 构造失败 | 启动边界 catch → 退出码 3 + detail |

## 5 异常策略

- **可预期失败用 `Error`**：参数非法、资源不足、队列满、客户端取消。
- **异常只允许来自**：标准库分配失败、第三方库抛出的异常、编程缺陷（越界/断言）。
- **线程体必须有兜底**：`SchedulerCore::run`、`StepExecutor::loop`、HTTP handler 三个入口各有一层 `try/catch`，catch 到就转成 `ExecutionFailed` 并**保证在飞请求收到终态事件**，禁止让异常逃逸到 `std::terminate`。
- **析构函数不抛**：清理路径一律 `noexcept`，失败只记日志。
- `noexcept` 只标在确实不抛的叶子函数上；标了 `noexcept` 又可能抛 = 直接 terminate。

---



## 6 日志

| 级别 | 场景 | 必带字段 |
|---|---|---|
| error | 线程兜底、启动失败、后端批失败 | `req_id`（如有）、`op`、`detail` |
| warn | KV 对账差异、sink 溢出、抢占超限、准入拒绝 | `req_id`、关键计数 |
| info | 启动摘要、监听、关停 | 无 |

热路径纪律不变（见 `docs/ci/log-policy.md` §4）：不逐 token 打印，错误日志只在失败分支触发。

## 7 验收清单

新增或修改错误路径时逐条自查：

1. 新 `ErrCode` 是否四处齐备（映射、名称、retryable、本表）？
2. `message` 是否能让客户端判断"改参数 / 重试 / 放弃"？
3. 第三方返回值是否在适配器内转换，原始 cause 是否进 `detail`？
4. 错误是否全程以 `Error` 传递，没有在中途退化成 `FINISH_REASON=error`？
5. 非流式是否按真实错误回状态码（不再 200 + 空 body）？
6. 流式是否在 `[DONE]` 前推一条 error 帧？
7. 回投/取消/关停事件是否走无损通道？
8. 是否有对应用例（成功 + 失败各一）？
