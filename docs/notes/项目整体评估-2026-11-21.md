## 0 一句话结论

这是一个**控制面工程质量明显高于普通课程项目 / 玩具项目**的单机推理实验床，也是一个**证据纪律罕见地好**的工程样本；但它仍然不是生产推理服务。



* 作为 “可运行、可复现、可学习的 Continuous Batching 参考实现”：**8.1/10，A-**

* 作为 “可对外提供 SLA 的生产服务”：**4.0/10，不合格**

它最值钱的部分不是吞吐数字，而是：线程模型、块表与抢占闭环、错误面契约、测试金字塔，以及 “发现口径错了就作废旧结论” 的证据链。最弱的部分是：**没有在完全驻留 GPU 的模型上证明 continuous batching 的正收益**，以及交付面（默认分支、发布标签、真后端 CI、部署验证）没有收口。

## 3 五个真正的强项

### 3.1 线程模型是 “想清楚了” 的，不是拼出来的

`HTTP 工作池 → SchedulerMailbox（有界，满即背压）→ 单线程 SchedulerCore → StepExecutor`。所有调度状态只在 Core 线程改，执行线程只做 `batch → decode_step → Completion 回投`。这套模型把最难的并发问题收敛成了 “一个写者 + 消息传递”，比 “到处加锁” 的调度器更容易验证。

几个细节能看出设计深度：



* Completion/Cancel/Shutdown 走 `push_critical` 无损通道，避免丢完成事件导致 Core 永久挂死；

* 准入用原子预留 `inflight_admissions_`，不是 “先查队列再入队” 的竞态写法；

* `shutting_down_` 原子化，HTTP 线程只读、Core 线程写；

* KV 峰值只在 Core 线程维护，通过统一 `publish_kv_usage()` 快照发布，避免多出口漏记。

### 3.2 调度闭环不是 “能跑”，而是 “有边界条件”

项目覆盖了多数同类实现会跳过的点：



* 请求数与 token 双预算独立判定（`INV-07`），不是只卡 `max_concurrency`；

* chunked prefill 与 decode 共享 token 预算；

* 准入前试算抢占、chunk 规划失败再抢占；

* 前缀缓存有 donor 槽、借用只下发一次、共享块引用计数释放；

* 抢占后 recompute 重放 prompt + 已生成 token，末 token 不重复采样；

* 容量门控按 `n_gpu_layers` 分显存池 / 内存池，不是单一 `safety_ratio`；

* KV 压力档实测触发了 10 次准入抢占、180 次 chunk 延后，40/40 成功。

这说明抢占 / 恢复不是 PPT 功能，而是被压力档打过的路径。

### 3.3 测试结构是金字塔，不是 “测试数量堆砌”

标签分布：`unit=114`、`contract=43`、`integration=14`、`e2e=1`、`asan=2`、`needs-gpu=2`、`slow=2`。这套结构与 “控制面实验床” 的定位匹配：



* unit 打纯逻辑：预算、切块、victim 选择、块表、配置校验；

* contract 打 HTTP/SSE 契约：413/404/405、model 回显、JSON 异常脱敏、charset、auth、rate limit、drain、slow client；

* integration 打进程级：准入、并发、chunked、metrics、matrix、config sources；

* 真模型 / 真服务用例缺环境变量时返回 77 跳过，不伪装通过。

特别值得肯定的是 “错误面规范 + 错误码路径逐一覆盖” 的做法。多数项目只测 happy path，这个项目把 413、429、503、404/405 的响应体形状当成契约在测。

### 3.4 证据纪律是最大差异化

阶段 8 最关键的动作不是加功能，而是**废掉旧口径**：prompt token 不再用 “非空白字符数” 估算，改为 `/metrics` 的 `prefill_tokens_total + prefix_hit_tokens_total + 生成 token`。旧 `40.96/50.28/65.94 tok/s` 与 “P=4 1.61×” 被明确作废。

这件事的含金量很高：



* 它意味着作者能区分 “数字好看” 和 “数字可信”；

* 它让后续所有性能结论有了统一会计口径；

* 它把 “负结果” 变成了可交付结论，而不是藏起来。

三轮独立 review（并发 / 生命周期、HTTP/SSE 契约、测试有效性）+ `evidence/phase8_*` 命令台账 + 原始日志，构成了可复核的证据链。这种工程习惯比多写 20% 功能更稀缺。

### 3.5 容量边界与降级是 “算过账” 的

27B dense 在 8 GB 卡 + 约 8 GB WSL 内存下，`ngl=0/8/24/32` 全部 `BLOCKED`，`ngl=16` `DEGRADED`，没有硬凑一个 “能启动” 的档位。容量判定按显存 / 内存双池计算，KV 预算按 `ctx × (concurrency + donor)` 而不是只按 `ctx × concurrency`。这比 “能跑就行” 的实现诚实得多。

## 4 真实性能：一个重要的负结果

### 4.1 已有数据



| 场景            | 配置                                      | 结果                                                                           | 能说明什么                         |
| ------------- | --------------------------------------- | ---------------------------------------------------------------------------- | ----------------------------- |
| 8B Q4 短档      | `ngl=24`，P=1/2/4，30 请求 × 32 token × 2 轮 | 总吞吐 26.266 / 29.659 / 25.656 tok/s；decode p50 12.83 / 6.61 / 3.10 tok/s      | **P=4 没有吞吐增益**，单路 decode 线性下降 |
| Q3\_K\_M 全量上卡 | `ngl=37`，`q8_0 KV`                      | decode p50 **52.14 tok/s**                                                   | 单路性能可以到 50+，但这是单流、全量驻留、第三方量化  |
| 长 prompt      | 关闭前缀缓存，约 522 token / 请求                 | TTFT p50 1,045 ms；decode 13.58 tok/s                                         | 长 prefill 的 TTFT 与短档不可混引      |
| KV 压力         | P=16 / ctx512                           | `kv_used_peak=461/512（90%）`；10 次准入抢占；180 次 chunk 延后；40/40 成功；TTFT p50 13.5 s | 机制能触发、能恢复，但服务质量不具备生产性         |
| 27B dense     | 8 GB 卡 + 约 8 GB WSL 内存                  | ngl=0/8/24/32 BLOCKED；ngl=16 DEGRADED                                        | 容量硬边界，不是调参问题                  |

### 4.2 怎么解读

**核心结论：在这台 8 GB 笔记本上，8B Q4 部分卸载时 continuous batching 没有带来吞吐收益。** 根因不是调度器写坏了，而是 13/37 层留在 CPU，decode 阶段被内存带宽卡住；batch 变大只增加了并行计算，没有减少每 token 的权重读取成本。P=4 时单路 decode 从 12.83 掉到 3.10，总吞吐还略低于 P=1，这是典型的 “部分卸载 + decode memory-bound” 结果。

这个负结果本身是有价值的：它回答了项目最初的问题 ——“在这台机器上 CB 到底带来多少收益”—— 答案是 “部分卸载档没有收益”。但它也意味着：



* 不能用这组数据证明 continuous batching 的正向价值；

* 不能把 Q3 的 52.14 tok/s 当作 “CB 的胜利”，它只是单流全量驻留的成绩；

* P2/P4 两轮偏差 8.9%/11.5% 属于 `high`，只能作趋势证据，不能做精细调参依据。

### 4.3 缺的那块拼图

要证明 CB 的收益，实验设置应该换成**完全驻留 GPU 的模型**：



* Qwen2.5-0.5B 或 1.5B 全量上卡，跑 P=1/2/4/8；

* 或 Q3\_K\_M `ngl=37` 跑 P=1/2/4 矩阵；

* 每档 5 轮，记录 GPU 温度 / 频率，报告中位数与四分位，而不是只看两轮偏差；

* 同时固定输出长度与 prompt 长度，避免长度分布污染。

没有这组数据，项目可以讲 “控制面机制正确”，但很难讲 “CB 在这台机器上更快”。这是当前评估里最重要的一条建议。

### 5.3 低优先级 / 范围性



* **swap 恢复未实现**：`RecoveryPath::Swap` 只有枚举与代价模型，调度路径固定 `choose(false, 1.0)` 走 recompute。阶段 3 文档已明确 “不在本阶段”，但在生产语义下这是缺失能力；建议在 README 的 “局限” 里写死，不要让读者误以为 swap 可用。

* **llama.cpp 内部头文件耦合**：块表与 cell 对账依赖内部 `find_slot`，升级必须复核。这是合理取舍，但应在依赖升级 checklist 里固定一条。

* **请求时限默认 120 s**：对长生成是硬边界，需明确 “超时是截断还是错误”，并在文档 / 测试中固定语义。

* **无 fuzz**：JSON/protocol 解析器值得加一轮 fuzz 或属性测试；当前主要靠 contract 用例。

* `scheduler.cpp`**&#x20;1,356 行**：不是缺陷，但是维护热点；新增策略应先补测试再拆职责，避免 “大文件 + 大改” 同时发生。

## 7 建议路线

### 7.1 如果只做三件事



1. **先修交付面（半天）**：把 `8` 最新 3 个提交合入 / 快进 `origin/main`，打 `v0.8.0` 标签；改 README 第 22 行为 “阶段 8 / 172 条 / 170 通过 / 2 跳过”；在 `CLI.md` §10 顶部标注 “以下为历史冻结条目，当前实现已支持 config 与 chat”。

## 8 最终判断

**这是一个值得讲、也经得起追问的项目，但要讲对故事。**



* 讲**控制面设计**：单写者 Core、有界 Mailbox、原子准入、KV 块表与抢占恢复；

* 讲**证据方法**：口径错了就作废旧结论、负结果照实写、跳过用例不伪装通过；

* 讲**边界判断**：27B 在当前硬件上没有可行档位，不硬凑；

* 不要讲 “生产级推理服务”，也不要把 Q3 单流 52 tok/s 当成 CB 的胜利。

按成熟度给一个更直白的定位：

> **实验床成熟度：L8/10；生产服务成熟度：L4/10。**
> 作为参考实现，可以通过；作为生产服务，当前应拒绝上线。

它距离 “优秀开源参考实现” 只差三件收尾事：默认分支与发布、文档一致性、真后端夜间回归。它距离 “生产服务” 差的是一个产品，而不是一个补丁。
