## 1. 已完成：Completion watchdog

### 契约

- 新配置 `--completion-timeout-ms` / `LLMOPT_COMPLETION_TIMEOUT_MS`，默认 `30000`，`0` 关闭，范围 `0..86400000`。
- Core 在提交批时记录 `pending_since_ns`；每 tick 检查，超时后：
  - 向对应请求的 sink 推 `EXECUTION_FAILED` 错误帧与 `FinishReason::Error`，HTTP 侧立即回 500；
  - `llmopt_completion_timeouts_total` +1；
  - 不提前 `finish`。执行线程可能仍持有该序列的 KV/后端槽，提前释放会 UAF；
  - 迟到 Completion 回到 Core 后走正常收尾，释放 KV 与后端槽。
- 永久挂死的执行线程无法安全强杀；watchdog 只保证客户端拿到终态，进程级隔离留给后续 runner 进程化。

### 测试

`tests/contract/watchdog_test.cc`：`SlowRunner` 每步睡 1.2 s，`completion_timeout_ns=300ms`。

断言：

- 1 s 内 sink 关闭且收到 `ExecutionFailed`，message 含“超时”；
- 迟到 Completion 后 `KVBlockManager` 空闲块回到总数；
- `core.shutdown()` 到 join 完成 <5 s；
- `llmopt_completion_timeouts_total == 1`。

## 2. 非流式断连取消：可行性结论

结论：**当前 `cpp-httplib 0.18.3` 无法在 handler 等待期间探测客户端断开**，本轮不实现。

证据与替代方案评估：

- `httplib::Request` 只有 `remote_addr/remote_port/local_addr/local_port`，不暴露 socket fd，也没有 `is_connection_closed()`。
- `httplib::DataSink::is_writable()` 只在流式 content provider 回调里可用；非流式 handler 拿不到 DataSink。
- 用 `set_chunked_content_provider` 把非流式改成 chunked：headers 与状态码在 provider 之前写出，生成阶段的错误无法再改 500，破坏现有错误契约。
- 通过 `/proc/net/tcp` + `Request` 五元组反查 fd：Linux-only、多连接竞争、维护成本高，且 Windows 构建不可用。
- 升级 httplib 到最新版也未暴露该 API；要么维护 fork，要么把网关换成可感知断连的代理/框架。

可行路径（按成本排序）：

1. 在反向代理层做断连取消：Nginx/Envoy 检测到 downstream 断开后取消 upstream 请求；服务端仍按现有 request deadline 收尾。不改 C++。
2. 换 HTTP 框架（Boost.Beast / Drogon 等）以拿到 socket 生命周期；改动面远大于本阶段。
3. 维护 httplib fork，给 `Request` 注入 socket 探针；升级依赖时需持续背补丁。

因此顺序调整为：真后端 nightly → 多租户 → soak；断连取消等网关方案落地后再做。

## 3. 决策口径（本轮采用）

- `control-port` 默认保持 `0`：不改变现有部署拓扑，避免 8081 端口冲突与“多开一个 listener”的隐性行为；需要隔离的部署显式开启。
- 进程内 TLS 定位“直连小部署/内网验收”；公网仍要求 Nginx/Envoy 终止 TLS 并做证书轮换。
- 非流式断连若未来实现，允许改变“断开后仍保留完整响应”的语义，以取消算力消耗为优先；但本轮未改。
