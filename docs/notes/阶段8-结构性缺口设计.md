## 0 三项的优先级与边界

| 项 | 缺口 | 影响 | 优先级 | 预估 |
| --- | --- | --- | --- | --- |
| R1-01 | Completion 丢失无超时看门狗 | 关停可能永久等待 | P0（可靠性） | 1–2 天 |
| R2-07 | 控制端点与推理共享单一线程池 | 慢连接可饿死 `/healthz`、`/readyz` | P1（可用性） | 1–2 天 |
| R2-03 | 非流式断连不触发取消 | 断连后 handler 占线程到 120 s | P2（资源） | 2–3 天 |

三项都不改变 HTTP/SSE 成功响应形状；任何契约变化（如非流式改 chunked）必须单独立项并先经用户确认。

## 1 R1-01：Completion 超时看门狗

### 1.1 现状与证据

- `mailbox_.push_critical` 当前无界，容量不足不会丢事件；但 Executor 的某一步若没有回投 Completion，Core 的 `pending_serials_/pending_remaining_/pending_step_` 无法清零，`shutdown` 的退出条件不成立。
- 现有代码路径下不可直接复现，属于“单步丢失”防御缺口，不是已确认线上缺陷。

### 1.2 设计

1. 新增 `--completion-timeout-ms`（env `LLMOPT_COMPLETION_TIMEOUT_MS`），默认 **0=关闭**，范围 0–600000。
2. Core 维护 `pending_since_`：每个在飞 serial 在首次提交 step 时记录 `steady_clock` 时间；每次收到该 serial 的 Completion 时刷新。`pump()` 每轮取最早未完成时间。
3. 超过阈值时调用 `fail_timed_out_serials(now)`：
   - 对每个超时 serial 走与正常完成相同的收尾路径，补一条 `Error{Timeout, "completion timeout"}`；
   - 将 serial 放入 `timed_out_` 集合，晚到的真实 Completion 只丢弃、不重复扣减；
   - 清 `pending_*`，归还 KV，保持 `running_` 计数一致。
4. 超时是**单步**口径，不是请求总时长；长 prefill 的每个 chunk 完成都会刷新，避免误杀合法长步。
5. `shutdown` 仍按现有排空流程；看门狗只负责把悬挂 step 收尾，不直接 `_exit`。

### 1.3 测试与验收

- 新增测试执行器：对指定 serial 的 Completion 只回投一次，第二次丢弃；构造“单步悬挂”。
- 断言：
  - `shutdown` 在 `timeout + 500ms` 内返回；
  - sink 恰好收到一条该 serial 的 `Timeout`，无重复 token；
  - `check_invariants` 的 KV/队列/活跃计数全零；
  - 未超时路径与基线逐 token 一致。
- 变异验证：把超时判断改成恒 false，测试必须红；改成重复收尾，KV 断言必须红。
- TSan 跑新增用例；默认关闭时全量 ctest 与阶段 3 基线完全一致。

### 1.4 风险

- 阈值过小会误杀真实慢步。默认关闭，先在 staging 设 10 s，观察 `step_ns_p99` 后再定生产值。
- 需要确保“超时收尾”和“正常完成”共用同一把状态锁/同一线程，避免双释放；若无法共用，保持 Core 单线程处理并在 `timed_out_` 上做幂等。

## 2 R2-07：控制端点线程隔离

### 2.1 现状与证据

- `src/http_server.cpp` 使用 `handler_threads = concurrency_limit() + 3`，`httplib::ThreadPool` 是单一共享队列，没有按路由预留。
- `httplib v0.18.3` 的线程池无路由优先级；慢读/慢写客户端可占满 worker，`/healthz`、`/readyz`、`/metrics` 只能排队。

### 2.2 分两阶段

**止血阶段（低风险，先做）**

1. 设置 `set_read_timeout` / `set_write_timeout`（建议 5 s / 5 s，可配置），限制慢连接占用上限。
2. 设置连接数上限，超过时快速拒绝并计入 `llmopt_http_rejected_total{reason="max_connections"}`。
3. 增加 `/healthz` 排队时间指标（从进入 handler 到开始处理），用于判断是否仍被饿死。
4. 不改变线程池容量与路由语义；验收：20 个慢连接下 `/healthz` 有响应且延迟有界，不出现全量超时。

**隔离阶段（需契约确认）**

候选方案：

- A：自定义 `httplib::Server` 子类/传输层，在任务入队前按路径标记 control/inference，两个队列、两个 worker 组；控制队列固定 2–3 个 worker。
- B：控制端点独立监听端口（如 `--control-port`），需要新增端口与部署配置，属于接入契约变更。
- C：fork/升级 httplib，暴露路由级任务元数据。

推荐 A：保持单端口与现有客户端契约，只改内部调度；若 httplib 不提供可重写的入队点，再评估 C，不选 B（除非用户明确接受双端口）。

### 2.3 测试与验收

- 集成测试：启动 20 个慢读连接占满推理 worker，同时请求 `/healthz`，断言 200 且 p99 < 100 ms；断开慢连接后指标归零。
- 压力测试：`/metrics` 与推理请求并发，控制端点错误率为 0。
- 回归：现有 13 个 integration 用例与 `auth_test` 全绿；`/v1/*` 路由与 `Allow` 头不变。

## 3 R2-03：非流式断连取消

### 3.1 现状与证据

- `httplib` 路由 handler 拿不到 socket；非流式 `drain_sink` 只能看 sink 帧、`is_closed()` 与 deadline，无法感知客户端 RST。
- 目前兜底是 `request_deadline_seconds`（默认 120 s），断连后线程仍可能占到生成结束。

### 3.2 方案比较

| 方案 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| A | 非流式也改成 provider 驱动，响应结束前由 provider 写一次 | 能复用写失败回调触发 `cancel` | 非流式响应变 chunked，部分客户端/网关不兼容 |
| B | 升级/改造 httplib，向 handler 暴露连接存活句柄 | 语义最干净 | 维护 fork，升级成本高 |
| C | 保持现状，只把 deadline 做成按端点可配并加观测 | 零契约风险 | 不真正取消，只缩短占用上限 |

**推荐顺序：C → A（开关默认关）→ B 仅在前两者不可行时考虑。**

### 3.3 设计（若走 A）

1. 新增 `--nonstream-provider-mode`（默认 `off`），开启后非流式走 `set_chunked_content_provider`；provider 在结果就绪后写唯一 JSON 帧。
2. 写失败/`is_closed()` 为 true 时调用 `core->cancel(req_id)`，并记录 `llmopt_nonstream_cancelled_total`。
3. 响应头仍为 `application/json; charset=utf-8`，但由于 chunked 不再有 `Content-Length`；在 `CLI.md` 标注为可选模式。
4. 默认 `off` 时保持现有 `Content-Length` 行为。

### 3.4 测试与验收

- 集成测试：stub 服务发非流式请求，收到响应头后 RST；断言在飞序列在 `deadline` 内清零、handler 线程释放、指标 `nonstream_cancelled` +1。
- 兼容测试：OpenAI Python/JS 客户端在 `provider-mode=on` 下能解析 JSON body；不能解析则 A 方案不发布。
- 回归：流式路径完全不受影响；非流式 body 字节与 `off` 模式一致（去掉 `Content-Length` 以外）。
