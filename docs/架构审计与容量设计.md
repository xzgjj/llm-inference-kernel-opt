# 8B 全量上卡验收 + 架构审计与容量设计

> 2026-11-21｜承接 `docs/8B-重测记录.md`。本轮做三件事：全量上卡（`-ngl 99`）验收、原始假设与契约逐条核对、为更大模型预留的容量设计。原始数据 `evidence/l1_p4_ngl28_t{8,12,16}.csv`、`evidence/l1_cb_curve.csv`。

## 1 全量上卡：本机不可行，且不是调参问题

实测（`-ngl 99`、ctx 1024、P=4、prefix 关）：`estimate: required=5370MiB free=4996MiB → BLOCKED`。

桌面常驻约 **3.1 GB**：Firefox 两进程、VS Code、飞书、豆包客户端（本会话宿主）、Typora、QQLive 等 27 个进程挂在 GPU 上。全关不现实——其中豆包客户端是这次任务的运行环境，杀掉即中断会话；VS Code 有未保存内容的风险。

按尺寸算，即使把桌面临时腾到 1 GB，8B Q4 也只剩 `8188-1000 ≈ 7.2 GB` 可用，而实际需要 `4794（权重）+ 576（KV）+ ≈330（compute buffer）= 5.7 GB`，勉强够；但桌面回到 3 GB 常态就不够。**结论：8B Q4_K_M 在这张 8GB 卡上“全量常驻”不是可交付的运行形态，正确目标是把部分卸载跑好。**

## 2 部分卸载的实测上限：线程数是最大杠杆

P=4、30 请求 × 32 token、ctx 1024、ngl 28/37：

| threads | TTFT p50 | ITL p50 | ITL p99 | decode tok/s | 结论 |
|---|---|---|---|---|---|
| 8（原默认） | 448.2 ms | 105.9 ms | 393.2 ms | 23.34 | 基准 |
| **12** | **347.8 ms** | **63.4 ms** | **230.1 ms** | **30.98** | **最优：+33% 吞吐，ITL p99 −41%** |
| 16 | 399.7 ms | 96.2 ms | 289.5 ms | 25.47 | 过度争抢，回退 |
| 12 + ngl 30 + q8_0 + donor 0 | **339.0 ms** | **69.2 ms** | **210.1 ms** | **31.07** | 当前最优（KV 半精度 + 30/37 层上卡） |

16 逻辑核里留 4 个给主线程与 GPU 喂数，12 是拐点。`run_cb_bench.sh` 的 `THREADS` 默认已改为 12。

> 口径提醒：上表 `decode tok/s` 由 ITL p50 反算，可信；本表不含总 token 吞吐。旧报告里的“总吞吐 65.94/31.07”混用了字符估算，阶段 8 起以 `tok_accounting=prompt_metrics` 为准。

对照 ngl 24（上一轮矩阵）：TTFT p50 711.7 ms → ngl 28 的 448.2 ms，多 4 层上卡就把 prefill 砍掉 37%。

## 3 审计：原始假设 vs 实测

| # | 原始假设 / 契约 | 实测 | 判定 |
|---|---|---|---|
| 1 | 0.5B 够用，换模型只影响数字 | 换 8B 后容量判据直接把服务判死（5946 > 5073） | **证伪**：模型规模会改变架构的有效性，不只是数字 |
| 2 | KV 是主瓶颈，水位线/抢占是核心机制 | P=4 时 `kv_util 2.88%`、`preempt 0`、`running_peak 4` | **证伪**：8B 上瓶颈在 CPU 卸载的 decode，KV 机制全程未触发 |
| 3 | 并发 4 吞吐 ≥1.5× | 真实 token 口径 P=4 25.66 vs P=1 26.27（**0.98×**）；旧“1.61×”是字符估算伪影 | **证伪**：部分卸载下并发不提升总吞吐 |
| 4 | KV 预算 = `ctx × concurrency` | 实际 `ctx × (concurrency + 4 donor)`；P=4 时一半是空占 | **口径不符**，见 §6 D3 |
| 5 | `safety_ratio` 0.80–0.85 够用 | 分池后 4955 MiB > 0.8×4996=3997，判 DEGRADED，靠 `mode=off` 才放行 | **区间过窄**，见 §6 D2 |
| 6 | 资源打点能证明显存峰值 | WSL 下 `vram_known=false`、`vram_peak=0`（pid 命名空间不匹配） | **证据缺口**，见 §6 D6 |
| 7 | step trace 能衡量调度开销 | `step_ns_p50=0.005 ms` 实为 `schedule_step_ns`（调度簿记耗时，微秒级合理），不是前向步耗时 | **命名易误读**，指标本身无误，报告需写明口径 |

## 4 契约核对

- `CLAUDE.md` §5「`required_bytes ≤ free × 0.80` 出三态」已补分池补充条款（本轮落地），但 **SPEC-4 正文未改**——属验收口径变更，需你签字后我才能改。
- `e2e_real_service_contract` 仍为 skipped：需要 `LLMOPT_E2E_MODEL` 之类的环境变量注入真模型，当前用例没有入口，属测试缺口。
- 8B 的 `estimate` 与实测偏差：`model_vram` 估 3729 MiB，实测 `CUDA0 model buffer 3456.52 MiB`，保守 8%；`kv_vram` 896 vs 实测 KV 侧约 960（含额外序列槽），方向一致。

## 5 更大模型的容量账（为本项目预留）

| 档位 | 4bit 权重 | KV/token | 本机可行性（2026-11-21 实测） | 定位 |
|---|---|---|---|---|
| Qwen3-8B | 4.7 GB | 144 KB | 部分卸载（ngl 24/37）可跑；全量上卡需 Q3_K_M | 现行证据档 |
| 27B dense | ≈16.4 GB | ≈262 KB（64 层估算） | **无可行档位**：ngl=0/8/24/32 `BLOCKED`，ngl=16 `DEGRADED`；最低档 host 仍 13003 MiB，远超约 8GB WSL 可用内存 | 只做容量验证，不跑吞吐 |
| 35B-A3B（Qwen4 候选） | ≈20 GB | 视架构 | 未实测；按 27B 结论，先过 host 内存判据再谈激活参数 | 未来最值得接入的档 |
| Qwen4-27B | ≈16 GB | 同上 | 同 27B：8GB 卡 + 8GB 内存无档位可行 | 等开源 |

实测命令（不加载权重，只跑启动预算判据）：

```bash
python3 scripts/bench/capacity_check.py \
  --server /root/llmopt-build/llmopt_server \
  --profile scripts/bench/capacity/qwen3-27b-dense-q4.json \
  --ngl 0,8,16,24,32 --out evidence/capacity_27b.csv
```

结果：`ngl=0/8/24/32` 全 `BLOCKED`；`ngl=16` 为 `DEGRADED`，`auto` 拒绝。**“大模型 + 8GB 卡”在本机是容量硬边界，不是调 ngl 能解决的问题**；表里旧的“32GB 内存可放”只是外部机器估算，不能用于本机结论。

三条设计约束随之确定：

1. **预算必须双池**（显存 + 内存），且能按 `n_gpu_layers` 变化重算——D1 已落地。
2. **KV 必须可压缩**：27B 在 ctx 1024、P=4 时 KV ≈ 2.1 GB，q8_0 可减半，否则内存里没有余量放权重。
3. **donor 槽必须按块表动态借**：固定 4 条满上下文在 27B 上等于 4×ctx×262KB ≈ 1 GB 空占。

## 6 设计决策（D1–D8）

| 编号 | 决策 | 状态 |
|---|---|---|
| D1 | 容量判据按 `n_gpu_layers/层数` 分池，显存池与内存池各自判硬超/软超；全量卸载保持单池 | ✅ 已落地（含 2 例单测） |
| D2 | 分池时 `safety_ratio` 放宽到 0.80–0.95，并允许显存/内存分别给值 | ✅ 已落地（上限 0.95；分池已按两池各自判据） |
| D3 | donor 槽可配（`--donor-slots 0..8`，default 4）；`0` 必须配 `--disable-prefix-cache`，否则保留序列占满后端槽位 | ✅ 已落地（实测踩到槽位耗尽后加了硬校验） |
| D4 | KV 缓存类型 `--kv-cache-type f16\|q8_0\|f32`，q8_0 把 KV 减半 | ✅ 已落地；该表 31.07 是纯 decode（由 ITL 反算），可信；旧“总吞吐 65.94”是字符估算口径，已作废，阶段 8 见 `docs/8B-重测记录.md` §5.3 |
| D5 | 部分卸载默认 `threads = min(12, nproc×0.75)` | ✅ 已在 bench 脚本落地；服务默认值待改 |
| D6 | VRAM 打点拆成 `llmopt_vram_process_mib`（能拿到才写）与 `llmopt_vram_device_mib`（整卡，WSL 可用），后者不得冒充前者 | ⏳ 待实现 |
| D7 | 复核 `step-trace` 写入点，`step_ns` 应记单步前向耗时（含 decode 与 prefill 分开） | ⏳ 待实现 |
| D8 | 每档模型在配置里声明 `ngl/ctx/threads/kv_type` 与预算上限，>27B 档只跑容量类用例，不产吞吐结论 | ✅ 已落地：矩阵字段进 `server_argv`；容量档用 `--model-profile` + `--capacity-only`，27B 档 JSON 在 `scripts/bench/capacity/`，实测见 §5 |
