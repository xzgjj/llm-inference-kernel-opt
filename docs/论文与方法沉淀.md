## 1 厂商标法对照

| 方法 | 代表实现 / 论文 | 核心机制 | 本项目对应 | 差异与结论 |
|---|---|---|---|---|
| 迭代级调度 | Orca（OSDI'22） | 以 iteration 为调度单位，新请求可在任一步插入；selective batching 拼不同阶段 | `SchedulerCore::pump` 每步重排 running/waiting；`SequenceGroup` 为调度单位 | 已实现同一骨架；本项目不做 selective batching 的算子融合，依赖后端按序列拼 batch |
| 分页 KV | vLLM PagedAttention（SOSP'23） | 逻辑块→物理块映射；按块分配，降低外部碎片；前缀块 COW 共享 | `KVCache` 块表、`block_tokens=16`、整块哈希前缀复用、引用计数 | 已实现逻辑块 + 整块前缀复用；**未实现** radix 树、块级 COW 写时复制、swap 到 CPU 的完整换入换出 |
| 抢占 | vLLM | 块不足时选 victim，整序列 swap 或 recompute | `preempt_for_waiting` / `apply_preemption`：释放整序列块、回 waiting、重算；连续抢占上限 3 | 本项目只有 recompute 路径，无 swap；代价模型 `recompute_ms` 只用于记录，不参与 victim 选择 |
| chunked prefill | Sarathi-Serve（OSDI'24） / vLLM | 长 prompt 切成 token 预算内的 chunk，与 decode 同步推进；以 stall-free 为目标 | `ChunkPlanner` 四档宽度；`max_num_batched_tokens` 预算；非末块只写 KV 不采样 | 已实现“decode 保位→在跑 prefill 下一 chunk→补新请求”；未实现 Sarathi 的 stall-free 全局编排 |
| 前缀缓存 | SGLang RadixAttention（NeurIPS'24） / vLLM | 前缀树按 token 粒度共享，cache-aware 调度优先复用 | 整块哈希 + donor 槽；`donor_slots=0` 时必须关前缀缓存 | 只支持整块（16 token）命中；无 radix 树、无 token 级部分命中；避免“逻辑块共享 = 物理零拷贝”的误判 |
| in-flight batching / paged KV | NVIDIA TensorRT-LLM | 运行中动态拼 batch、分页 KV、FP8/INT4、KV reuse | 本项目只做调度层，后端交给 llama.cpp | 不复刻 TensorRT 的 kernel/fusion；本项目价值在“可解释的调度与容量判据” |
| 部分卸载 + 量化 KV | llama.cpp | `n_gpu_layers` 分层卸载；`f16/q8_0/f32` KV；CPU/CUDA 混合缓冲 | `--n-gpu-layers`、`--kv-cache-type`、启动预算按层切分 | 已复用；本轮实测证明“全量上卡 + Q3_K_M”是单路 50 tok/s 的关键组合 |

## 2 本项目已落地、可复用的方法

### 2.1 容量判据先于压测

启动 L2 用 GGUF 元数据 + 真实可用显存/内存做三态判定（`ELIGIBLE / DEGRADED / BLOCKED`），再决定是否加载。方法要点：

- 模型字节用文件大小，KV 字节用 `层 × ctx × KV 头 × (k+v) × 元素字节`；`q8_0` 按 34/32≈1.0625 B/值，不能沿用 f16 的 2 B。
- 分池预算：`model_vram + kv_vram` 与 `host_model + host_kv` 分别对 `free × safety_ratio` 校验；任何一池不够都拒绝。
- 容量档位（`--model-profile`）允许权重不在本机时只验证“这档模型 + 这张卡”的可行性；结论只覆盖容量，不覆盖吞吐。

可复用点：任何“大模型 + 小卡”评估，先把容量判据和吞吐结论分开，避免用一次 OOM 或一次慢速跑替代边界分析。

### 2.2 证据列必须能归因

本轮把显存拆成三列，而不是一个“GPU 峰值”：

- `vram_peak_mib` = `CUDA0 model + KV + compute` 缓冲之和，进程可归因；
- `vram_peak_scope` 显式区分 `buffers / buffers_partial / unknown`，stub 或无 CUDA 日志禁止写 0 冒充实测；
- `vram_device_peak_mib` 是全卡口径，只用于观察桌面扰动。

方法结论：WSL 下 `nvidia-smi --query-compute-apps` 拿不到 pid 时，llama.cpp 的 buffer size 日志是比“全卡 used”更可信的证据源；但它是**加载/预留时点**的常驻，不等于运行峰值，需在文档里写清口径。

### 2.3 指标要区分“总 token”与“纯 decode”

`total_tok_s = (逻辑 prompt tokens + generated) / wall`，会被长 prompt 抬高；单路 decode 能力要用 `1000 / ITL_p50` 或 `generated / decode_wall`。本轮 Q3_K_M 的 52.14 tok/s 是**单路纯 decode**，不是总 token 吞吐；两者不能混引。

**口径修正（阶段 8 实测踩坑）**：prompt 侧不能再用字符数估算。中文 BPE 下非空白字符数约为真实 token 的 2.6 倍，短档总吞吐会被整体抬高 2 倍以上。正确口径是服务端 `llmopt_prefill_tokens_total`（实算）+ `llmopt_prefix_hit_tokens_total`（命中复用）+ 生成 token；矩阵新增 `tok_accounting=prompt_metrics/char_estimate` 标明每行来源，`char_estimate` 行不得单独引用。修正后同一短档的 P=1 总吞吐从 54.1 降到 26.3 tok/s——**旧数字作废，不是机器变慢**。

### 2.4 压力要打到块表水位，不是“并发数字大”

只把 `max_concurrency` 调大不等于 KV 压力：准入按 `prompt + max_tokens` 预留，短 prompt 下块表利用率很低。要触发抢占，需要同时满足：

1. 单请求 `prompt + max_tokens ≈ ctx_tokens`，让每条运行序列吃掉整槽 KV；
2. `max_concurrency` 接近块池可容纳的满槽数；
3. 等待队列非空，使“完成一个→补一个”时 free 块仍低于 `need + watermark`。

本轮第一次 P=8/ctx1024/960 字符 prompt 只到 201/512 块（39%），没有触发抢占；换成 P=16/ctx512/1200 字符（≈467 真实 token）/chunk64/q8_0 KV 后，才把水位打到 **461/512（90%）**，40/40 成功，触发 10 次准入抢占、180 次 chunk 延后、296 个 chunk 步，无连续抢占上限错误。这是“参数看起来够、实际没压力”的典型反例。

关键配方（8B / 512 块池）：

- `ctx=512`、`max_tokens=32`、`max_num_batched_tokens=256`、`chunk_size=64`；
- 每请求真实 prompt ≈467 token，准入按 `prompt+max_tokens` 预留，一条序列吃掉近整槽；
- `P=16` 让 16 条满槽序列 + 等待队列同时存在，块表只剩水位线以下余量；
- 只有这时 `preempt_admission` 才从 0 变为 10；若 prompt 只有 360 token 或 P=8，水位停在 39%–84%，抢占永远为 0。

## 3 不可直接复用的部分

- **swap 换入换出**：需要后端支持把 KV 块搬到 host 再搬回；llama.cpp 当前接口没有稳定暴露，强行做会退化成整序列重算。
- **radix 前缀树 / token 级共享**：需要块表从“整块哈希”升级为“树 + 部分块引用”，与当前 `blocks_for_tokens` 的预留模型冲突，属于下一阶段重构，不在本轮硬塞。
- **PD 分离 / 多机**：超出单机 8GB 卡的范围；本轮容量结论已经说明 27B 在本机不可行，PD 不能改变单卡显存约束。
- **自研 CUDA 算子**：项目范围明确排除；调度层收益已验证，继续往 kernel 走会偏离“可解释的连续批处理”主线。

## 4 本轮实测结论（8B / 8GB 卡 / WSL CUDA）

### 4.1 Q4_K_M 部分卸载（ngl=24，short 128 prompt，P=1/2/4）

| P | 状态 | TTFT p50 (ms) | ITL p99 (ms) | 总 token 吞吐 (tok/s) | 单路 decode p50 (tok/s) | 进程显存 (MiB) | 两轮偏差 |
|---|---|---|---|---|---|---|---|
| 1 | ok | 208.366 | 131.897 | 26.266 | 12.83 | 3804.52 | ok |
| 2 | ok | 445.847 | 324.689 | 29.659 | 6.61 | 3896.58 | high |
| 4 | ok | 913.761 | 657.152 | 25.656 | 3.10 | 4080.33 | high |

> 真实 token 口径下，总吞吐不再随 P 单调上升：P=1/2/4 为 26.3/29.7/25.7 tok/s，P=4 反而略低；单路 decode 从 12.8 线性降到 3.1，说明 ngl=24 的 CPU 侧带宽已经饱和，拼 batch 只增加每步时间，不增加总 token 产出。P2/P4 两轮偏差 8.9%/11.5% 为 `high`，只作趋势证据，不作 SLA 结论。

### 4.2 Q3_K_M 全量上卡（ngl=37，q8_0 KV，ctx=512，P=1，32 请求 × 128 token，两轮）

| 指标 | 实测 |
|---|---|
| 单路 decode p50 | **52.14 tok/s**（ITL p50 19.178 ms） |
| 总 token 吞吐 | 58.424 tok/s（真实口径） |
| TTFT p50 / p95 | 29.308 / 110.480 ms |
| ITL p99 | 23.020 ms |
| 进程显存 | 4193.12 MiB（`buffers`） |
| 两轮偏差 | TTFT 4.081% / ITL 2.044% / 吞吐 3.094% → ok |

结论：**Q3_K_M + 全量上卡达到并超过 50 tok/s 单路目标**，可作为“精度降档”对照档；代价是 4bit 量化精度损失，不能作为默认生产档。为在桌面占用约 3.6 GB 时留出显存余量，本轮把 ctx 从 1024 降到 512；decode 由权重带宽主导，ctx 对单路速度影响很小，但 512 不能用于长上下文结论。

### 4.3 27B dense 容量边界（声明 16.4 GiB / 64 层 / 8 KV 头，真实空闲显存 5.2 GiB）

| ngl | 判定 | 模型显存 (MiB) | KV 显存 (MiB) | host (MiB) | 原因 |
|---|---|---|---|---|---|
| 0 | BLOCKED | 0 | 0 | 17337 | host 超可用内存 |
| 8 | BLOCKED | 2099 | 68 | 15170 | host 超可用内存 |
| 16 | DEGRADED | 4198 | 136 | 13003 | 分池超 `free×safety`，auto 拒绝 |
| 24 | BLOCKED | 6297 | 204 | 10836 | 已卸载部分超可用显存 |
| 32 | BLOCKED | 8396 | 272 | 8668 | 已卸载部分超可用显存 |

结论：在 8GB 卡 + 约 8GB WSL 内存下，27B dense 没有任何档位能进 `auto` 预算；最低可行的 ngl=16 仍是 `DEGRADED`，且 host 13.0GB 远超真实可用内存。**“大模型 + 8GB 卡”不是调 ngl 能解决的，是容量硬边界。**

### 4.4 KV 压力 / 抢占 / chunk 权衡（P=16，ctx=512，q8_0 KV）

| 指标 | 实测 |
|---|---|
| 成功 / 总请求 | **40 / 40** |
| `kv_used_peak` | **461 / 512 块（90%）** |
| 准入抢占 `preempt_admission` | **10** |
| chunk 延后 `chunk_deferred` | **180** |
| chunk 步数 `chunk_steps` | **296** |
| 连续抢占上限错误 | **0** |
| TTFT p50 / p95 | 13533.706 / 23757.599 ms |
| ITL p99 / p50 | 1833.804 / 793.7 ms（≈1.26 tok/s/路） |
| 总 token 吞吐 | 190.9 tok/s（prompt 主导，40×467=18670 prefill token） |
| 进程显存 | 3570.96 MiB（`buffers`） |

结论：这组参数**真正触发了块表水位**，不是“并发大但 KV 空闲”。代价是 TTFT 从 0.2 s 量级涨到 13.5 s、单路 decode 降到 1.26 tok/s；抢占与 chunk 是“高水位下的可用性换延迟”，不能作为常规吞吐配置。

### 4.5 长 prompt 真实 prefill（P=1，关闭前缀缓存）

| 指标 | 实测 |
|---|---|
| prompt / 请求 | 522 token（1400 非空白字符） |
| 成功 / 总请求 | 10 / 10 |
| TTFT p50 / p95 | 1045.205 / 1107.186 ms |

## 5 可复用清单（按优先级）

1. **三态门控 + 分池预算**：先判容量，再谈性能；`q8_0` KV 必须按 1.0625 B/值估算。
2. **进程级显存三列**：buffer 日志拆分 + scope，避免全卡峰值冒充进程占用。
3. **双口径吞吐**：`total_tok_s` 与 `decode_p50` 并列，禁止只报一个数。
4. **压力参数配方**：`prompt+max≈ctx`、`P≈块池满槽数`、等待队列非空，三者缺一不可。
5. **容量档位 JSON**：权重不在本机也能复现容量结论，字段固定为 `file_bytes/block_count/head_count/head_count_kv/key_length/value_length`。

## 6 后续可写论文/工程题

- 整块前缀复用 vs radix token 级共享：在 8GB 卡上做命中率-碎片-重算三方权衡；
- 抢占 victim 选择：当前按最晚进度/最大块数，未把 `recompute_ms` 纳入代价，可用 trace 做离线策略评估；
- chunk 宽度与 watermark 的联合调参：本轮只证明能触发，未做 Pareto；
- 容量判据的置信区间：用真实 buffer 日志校准估算误差，给出“预算余量”而不是单点阈值。
