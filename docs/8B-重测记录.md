## 0 结论（已按真实 token 口径重写）

| 并发 P | TTFT p50 | ITL p99 | 总 token 吞吐 tok/s | 单路 decode p50 | 复现偏差 |
|---|---|---|---|---|---|
| 1 | 208.4 ms | 131.9 ms | **26.266** | 12.83 tok/s | ok |
| 2 | 445.8 ms | 324.7 ms | **29.659** | 6.61 tok/s | high（8.9%） |
| 4 | 913.8 ms | 657.2 ms | **25.656** | 3.10 tok/s | high（11.5%） |

1. **真实口径下并发不提升总吞吐**：P=1/2/4 为 26.3/29.7/25.7 tok/s，P=4 反而略低。原因是 ngl=24 时 13 层留在 CPU，decode 被内存带宽卡住；拼 batch 只把每步时间拉长，单路 decode 从 12.8 线性降到 3.1。
2. **旧“P=4 1.61×”是度量伪影**：字符估算给每条请求加了固定的大 prompt 项，掩盖了 decode 退化。这条结论已从项目叙事中移除。
3. **部分卸载的合理目标不是总吞吐，而是“能跑 + 延迟可解释”**；要 50 tok/s 单路必须全量上卡（Q3_K_M，见 §5.3）。
4. P2/P4 两轮偏差 8.9%/11.5% 为 `high`，只作趋势证据；P1 的 2.0% 偏差可作单路基线。

## 2 被 8B 暴露出来的四个问题（按严重度）

### 2.1 容量判据是单池，8B 全量卸载必被硬拦（已修）

原口径 `required = file_bytes + kv` 全部压在**空闲显存**上：`4794 + 1152 = 5946 MiB > free 5043~5073 MiB`，`decision=BLOCKED`，`--mode off` 也不放行。而实际 `-ngl 24` 只有 3015.58 MiB 上卡，其余在内存里。**这台机器上 8B 连启动都做不到，不是性能问题，是预算模型问题。**

改造：`EstBudget` 增加 `model_vram_bytes / kv_vram_bytes / host_bytes`，按 `n_gpu_layers / block_count` 拆分，显存池与内存池各自判据；`n_gpu_layers ≥ 层数` 时保持原单池行为。启动日志新增 `estimate-split:` 一行：

```text
estimate: model=4794MiB kv=1152MiB required=5946MiB free=5269MiB safety=0.8 decision=ELIGIBLE
estimate-split: model_vram=3196MiB kv_vram=768MiB host=1982MiB
```

估算 3196 MiB vs 实测 `CUDA0 model buffer 3015.58 MiB`，偏保守 6%，方向正确。

### 2.2 donor 槽预分配 4 条满上下文，8B 上吃掉 24% 的 KV 预算（未修）

`n_seq_max = concurrency + kDonorSlots(4)`，每条按 `ctx_tokens` 全额预留。`ctx=1024, P=4` 时 KV 估到 **1152 MiB**，其中 576 MiB 是 4 个 donor 槽。0.5B 上这是 50 MB 量级的噪声，8B 上它等于 3 个真实请求的 KV。建议 donor 槽按块表动态借用，或按 `min(4, 剩余块/每槽块数)` 收缩 —— 需要改 KV 语义，未擅自实施。

### 2.3 WSL 下 VRAM 采样全空，证据链缺显存峰值（未修）

矩阵 `resource_peak` 三个并发档都是 `vram_known=false, vram_peak=0`。`resource.cpp` 用 `nvidia-smi --query-compute-apps=pid` 按 pid 匹配，WSL 里进程 pid 与 Windows 侧 pid 不是同一命名空间，永远匹配不到。建议：WSL 下改读 `--query-gpu=memory.used` 并标注“整卡”语义，或在 `capability_snapshot` 里写 `probe=degraded`。

### 2.4 step trace 时间口径对不上

`step_ns_p50 = 0.005 ms`、`p99 = 0.04 ms`，而实测 ITL p99 是 407 ms。三个数量级的差说明 trace 里 `ns` 记的不是前向步耗时（更像时间戳差值或单 token 片段）。这条指标目前不能进报告，需要复核 `step-trace` 的写入点。
